# 待辦與改進方向

跟目前主流 harness（Claude Code、Agent SDK 等）比較後整理的改進方向，以及其他還沒處理的項目。做完的項目移到最下面的「已完成」，並寫上 commit。

## 改進方向

### 1. 串流顯示劇情

- **問題**：現在等 AI 把整段生成完，才開始打字效果，等於等兩次。紀錄裡一回合常要 10～20 秒，幾乎都是 Gemini 在生成。
- **做法**：一邊生成一邊顯示 `narration`，第一個字預計 1～2 秒就會出現。狀態變化（傷勢、背包、里程碑）等整段完成後，照樣由程式驗證再套用，護欄不受影響。
- **難點**：劇情和狀態變化包在同一個 JSON 裡，要從還沒生成完的 JSON 中取出 `narration`。共用層的 `show_narration()` 要改成可以一段一段送文字；終端機和網頁的打字效果也要跟著改。
- **優先**：最高。直接對應「等很久」的問題，而且不用改架構。

### 2. 評估（evals）

- **問題**：測試只驗證程式規則，不驗證 AI 寫得好不好。改提示詞或題材包後，只能靠實際玩一局來判斷有沒有變差。
- **做法**：準備一組固定情境（例如第 3 回合主角重傷、第三幕該揭露真相、多人模式其中一人倒下），修改後讓 AI 跑一遍，再用程式或另一個 AI 檢查：
  - 有沒有太早寫出結局
  - 第三幕有沒有揭露真相、有沒有呼應伏筆
  - 有沒有替玩家決定行動或感受
  - 長度與語氣是否符合題材
- **注意**：會用到真的 API、會花錢，所以只在改提示詞時手動執行（例如 `just eval`），不放進一般的 `uv run pytest`。

### 3. 把提示詞從程式碼拿出來

- **問題**：`SYSTEM_PROMPT` 與各種指示寫在 `engine.py`、`party.py` 裡，`engine.py` 已經將近 700 行，提示詞的修改混在程式的修改裡。
- **做法**：跟題材包一樣，把提示詞放成獨立的檔案（例如 `src/story/prompts/`），程式只負責組合。這樣可以單獨檢視提示詞的修改紀錄，也方便搭配評估。

## 其他待辦

- [ ] **用真的手機試網頁版**：中文輸入法選字、觸控捲動、對話框從下方滑出。無頭 Chrome 只模擬過手機尺寸。
- [ ] **用真的 AI 玩一局網頁版**：生成中的進度文字、長段劇情、限時倒數、結局分段。
- [ ] **「2」對應到第二個選項的規則有兩份**：核心的 `action_for()`，以及線上多人時 `client.py` 的 `echo_for()`。可以由核心匯出一個小函式讓兩邊共用。影響很小，只影響送出前先顯示的「› 往上爬」。
- [ ] **伺服器啟動時印出區網網址**：現在印的是 `http://0.0.0.0:8080`，要自己查這台電腦的區網 IP。

## 不打算做

- **子代理、多代理**：每回合寫一段劇情，拆成多個代理只會更慢、更貴。
- **讓 AI 用工具直接改狀態**（自己查背包、自己判定傷勢）：生死、傷勢、背包由程式把關是這個專案的核心設計，交給 AI 等於拿掉護欄。
